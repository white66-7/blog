## 创建
创建的命令语句是`git init`，默认把当前目录初始化为仓库，也可以在后面加名字，新建一个文件夹放置.git文件夹
```bash
git init
```
如果想对别人的项目二次开发可以在`git clone`语句后加入别人的仓库地址克隆别人的仓库，这里拿我的博客仓库举例子。
```bash
git clone https://github.com/white66-7/blog.git
```
如果要向 GitHub 推送代码，通常需要先配置提交作者信息，包括用户名和邮箱。它们会记录在 Git 提交中，用于标识提交者；这些通过 git config 设置，依旧拿我举例子：我叫white66-7，邮箱是white667189top@gmail.com，对应的git语句就是：
```bash
git config user.name "white66-7"
git config user.email "white667189top@gmail.com"
```
这里值得一提的是，在`git config`后加选项`--global`，可以给以后创建仓库的用户名和邮箱设置默认值。
## 工作分区
git的数据管理将文件分为三个状态，分别是工作区，暂存区和本地(云端)仓库，他们分别在根目录、`.git\index`、`.git\objects`文件目录下
<img src="/messages/21/git.webp" style="width: 100%;" />

从工作区转到暂存区的语句是`git add`,后面跟文件名可以指定具体文件或路径。最常使用的是`git add .`语句：把所有没被`.gitignore`文件剔除并且改动了的文件放入暂存区。

从暂存区到仓库的语句是`git commit`语句，输入后git会打开默认编辑器，让你填写提交说明。可以通过直接`git commit -m  '这次我更改了...'`一次性操作。

我当时的疑惑是：为什么要有暂存区？后来我明白：如果没有暂存区，`git commit` 相当于把工作区里的所有改动一次性打包提交；但写代码时常常东改改、西改改，通过暂存区可以实现选择性提交，把较大的改动拆成多个清晰的提交，并且在提交前预览要提交的内容。

如果要把本地仓库的提交上传到云端，用的是`git push`语句。

如果要查看现在这三个分区的状态，可以用`git status`语句。查看当前在哪条分支，已修改但未暂存的文件，以及暂存区状态。

## 版本管理 
Git 作为版本管理工具，每次提交会对应一个唯一的哈希值，类似数据库中的 `UUID` 字段，用于标识版本。查看提交历史可以使用`git log`；
>commit f2581babefab255671b7c70348758e7be64d4da5  
>Author: white66-7 <邮箱>  
>Date:   Wed Oct 28 22:41:31 2026 +0800  
>更新网页图标padding，新开第21篇文章及相关内容  

加上 `--oneline` 参数后，可以查看更简洁的描述。

>d6d1174 修复了移动端隐藏与显示导致的空白曾，调整了首页所有组件的布局，增加缩放系数

回退版本可以使用 `git reset`，查看差异可以使用 `git diff`，删除文件可以使用 `git rm`，还可以通过 `.gitignore` 文件忽略某些文件。下面谈谈对这些命令的用法及理解。
### 回退
回退存在三种形式，对应`--hard`、`--soft`、`--mixed`参数，`hard`参数表示回退到指定版本并且丢弃暂存区与工作区的全部修改。`soft`参数相反，保留暂存区与工作区的修改；`mixed`是默认参数，表示丢弃暂存区的修改，但是保留工作区的修改。

在上述这些参数后面跟版本号用来指定回退版本，由于默认情况下是`HEAD`参数，表示当前版本，所以当我们仅仅输入`git reset`时，相当于——不版本回退的同时取消暂存区修改。

在个人开发中，版本回退其实用得不多。我有过两次后悔对代码改动的时候，但说来搞笑，我没有使用 Git 的回退命令，而是直接把旧版本的内容粘贴过来，覆盖掉当前文件，在适当修改后，重新提交覆盖当前版本。
### 版本差异查看
这个功能还是非常重要的，可以视奸某些项目每次提交改动了哪些文件；在研究良久并修改后查看一下与最新版本的差异的情境下，是一件很有成就感的事情。

我们不仅可以查看文件在两个特定版本下的差异，还可以查看文件在两个分支间的差异。

但是大部分的代码开发工具都主动适配这一功能，只有在服务器上可能会用到`git diff`命令。

第一行返回变更的文件，第二行是通过哈希算法生成的部分哈希值以及文件的权限；最后面是修改的内容。

### 忽略
文件忽略是 Git 的一项基础功能，常见的使用场景有两个：其一，通过`npm`管理的外部依赖常位于`node_modules`目录，由于其体积庞大且可通过命令重新生成，无需纳入版本控制；其二，本地测试所需的密钥，常保存在 .env.local 文件中，出于安全考虑不应被提交。

诸如此类无需版本控制的情境还有很多。为此，我们需要创建`.gitignore`文件，在其中配置不需要被 Git 追踪的文件或目录：如果是文件夹则在末尾处添加`/`，如果是文件直接输入文件名。
```text
node_modules/
.gitignore
``` 
还有一些技巧：
- 通配符`*`用于匹配任意字符
    - `*.log` 表示忽略以`.log`结尾的文件
    - `temp*` 表示忽略以 `temp`开头的文件
-  例外规则`!`
    - 追踪被通配符包含的文件
像下面就是忽略`.env`开头的文件，但仍追踪`.env.example`文件。
```text
.env*
!.env.example
```
### 删除
我最初学到删除时的疑惑是：直接手动把文件删掉不就行了？

实际上这两者的不同之处在于:手动删除只改变了工作区；而输入`git rm`时，Git 会自动将文件从工作区移除，并把该删除动作同步到暂存区。

另外，Git 有个特性：已经被追踪过的文件，事后将其加入 `.gitignore`，规则无法生效。如果想让忽略生效，需要使用 `git rm --cached`后加文件名来解除追踪特定的文件。
## Github
开发时，我们经常需要把本地代码上传到云端。这既能向更多人展示我们的项目，同时也是一种备份手段，防止未来本地硬盘出问题导致代码丢失。

GitHub 有两种连接方式：`HTTPS` 和 `SSH`。前者在推送代码时需要验证账号密码，也就是说，在国内网络环境下,往往需要科学上网才能推送。

后者（SSH）则不需要这么麻烦。我们只要在 GitHub 设置里配置好公钥，之后的推送就会自动进行安全验证：每次交互时，GitHub 会生成一段“挑战”数据，用公钥加密后发送到本地；本地收到这段数据后，用私钥进行处理后发送回去，最后 GitHub 用公钥验证结果。

第一次使用 `SSH` 时，需要在本地生成公私密钥：其中`-t ed25519`指定密钥的加密算法,`-C "我的邮箱"`来添加备注
```bash
ssh-keygen -t ed25519 -C "white667189top@gmail.com"
```

生成的文件一般放在 `C:\Users\12625\.ssh` 目录下。其中，以 .pub 结尾的文件是公钥，我们需要复制里面的内容，并在 GitHub 后台配置。

后续就可以通过`git remote add`语句后添加对应的远程仓库名实现`SSH`连接。
## 分支与合并
分支与合并是团队协作的基础，也是 Git 最重要的特性。大部分开发工具对分支都有图形化呈现，你可以很直观的感受到这个功能。

常见的场景是：多个开发者在各自的分支上开发不同的功能，测试通过后再合并到主分支上。老实说，个人开发不太常用到这个功能，我只尝试过一次：博客的原型是一个音乐播放器，我用两个 GitHub 账号开了两个分支进行开发并最终合并。但想必这在互联网公司绝对是一项基本且重要的技能。

当然，伴随着团队协作，这个技术栈也诞生了不少梗。 比如`git commit -m`后陷入深度思考，又或是解决合并冲突的终极兵器`git push --force`，

新开一个分支用到的命令是 `git branch` 后加分支名。后续要转到其他分支上进行开发通过 `git switch` 加分支名来实现。值得一提的是，git checkout 同样可以切换分支，但通常不使用它。因为 `git checkout` 承担的功能太杂了,不小心敲错参数可能会引发一场蝴蝶效应。

接着就是合并。正常情况下：两个分支修改的文件或代码位置不同，输入 `git merge` 加上分支名完成合并。

但以下两种情况下，会发生合并冲突：第一种是两个分支同时修改了同一个文件的同一行代码。输入`git merge`后 Git 不知道该保留哪一个改动而报错。此时注意的是，那个需要改动的文件大概呈现下面的样式。我们需要手动编辑矛盾的代码段，接着暂存提交。
<img src="/messages/21/merge.webp" style="width: 100%;" />

另一种情况是本地与远程仓库的冲突。举个真实的例子：在 GitHub 网页上修改 Readme.md，在本地也改了Readme.md。此时把本地的修改 push 到远程时，Git 会拒绝。我们需要先`git pull`拉取远程代码，接着打开Readme.md文件，向上面一样修改矛盾处后暂存提交。

最后是一个我从没用过的语句: `git rebase`，它因下述两个场景而存在——当频繁合并分支时，Git的历史记录会像蜘蛛网一样，并多出很多无意义的Merge branch 'xxx'的记录；写代码时，我们经常会有一堆无意义的提交，比如如下两个提交`git commit -m "修个 bug"`、`git commit -m "漏了写分号"`。

`rebase`美观git树的点在于它将分支从底部拔起，接在主分支的顶端。操作就是切换到自己的分支后输入`git rebase main`语句。但是可想而知在某些情况下，这对于协作开发无疑是毁灭性的混乱:推上去却发现主干的历史已经被强行改写，导致所有人的本地记录全部错乱……

压缩提交一般使用`git rebase -i HEAD~2`交互式变基语句：其中HEAD指向当前最新提交,`~2`表示回退两步，`-i`是interactive的缩写表示。输入后编辑器中大概是这样的
```text
pick 1a2b3c4 修改了首页的布局
pick 5d6e7f8 修复了首页布局的一个小bug
```
将第二个pick(保留这个提交)换成squash(把这个提交合并到上一个提交里)并提交。
