## 简易步骤（vercel）
如果你写代码，那么你一定会先去学习git相关的知识。

接着会去理解云端git的概念，注册一个Github账号作为你的云端项目存放处。

老实说，其实我学的时候，觉得git的逻辑，特别是里面的brach分支特性，有些许对应我之前学达芬奇剪辑时调色部分的一级二级调色：都可逆，步步留痕，可视化...

倘若你的代码都推送到github,github会自动解析你的代码框架并且显示出来。就像下面这个一样。
![笔记1](/messages/10/languages.webp)

接着你登录vercel这个网站，注册一个账号，绑定你在Github上的项目，它就会自动解析你的项目，扔给你一个网址，这时候如果代码没啥问题，步骤也没啥问题，直接搜他给你的网址就能看到你的代码所呈现的视图了。

那么vercel究竟做了些什么呢？

我的理解是：它首先通过api去获取Github解析你项目得出来的技术栈,接着它根据技术栈自动运行对应的脚本包含配置环境，安装库，打包，呈现等等操作并最终分发你一个域名地址，这样的一条龙服务非常方便快捷。

对于静态的代码而言，访问者只能看网站，并不存在上传文件等操作，因此所需要的GPU算力不大，普通免费版就已经能满足需求。
## 国内建站
如果你已经习惯了vercel的模式，但是又受不了vercel部署的网站由于服务器在国外,所以要挂梯子才可以访问的话。那么可以尝试国内的平替——腾讯云EdgeOne Pages,但是老实说我没有切身体验过。

其实未来我想把这个网站做成比较基础的可交互模式,最初的设想是：

给每个访问者登录的选项，一般是Github账户登录。

给每篇文章做一个浏览量显示,至于点赞就比较纠结到底做不做。

在关于界面做一个留言版，登录的访问者可以留言。

为了达到这样的效果，就需要我有一个服务器实时在线，来处理访问者发送的各种请求，同时也要去发起一些Api请求。服务器我最终选择了阿里云，因为它有个学生福利——300的额度。

这个b站视频讲得还算蛮不错的。我就说说其中我自己的理解。

首先来说，服务器采用的是Ubuntu的linux操作系统，主要是由于命令行视图：服务器显示就像是一个终端，这样一是可以很方便的输入指令查看修改等等。其二是不用向windows一样加载图形界面还有后台进程，节省的GPU算力。还有一点就是linux操作系统的稳定性极高，似乎天生就是为了服务器这样的大型数据管理机使用的。

其次是为了更好的管理服务器，一般都是要给服务器下载<a href="https://www.bt.cn/" target="_blank" rel="noopener noreferrer">宝塔</a>——服务器可视化管理面板。
那么为什么要去调服务器安全组的端口呢？其实可以这样理解：安全组就像是保安，对于访问的陌生人，他会仔细对照你给出的规则,查看让不让它进去。

宝塔使用这个8888这个极度偏门的端口，而对于普通用户在浏览器中输入域名——imdaio.com,一般浏览器会自动补全为https://imdiao.com:443,通过443端口访问，但是这时候如果你的网站没有SSL证书，那么就补全为http://imdiao.com:80，通过80端口访问。

当访问没有SSL证书的网站，也就是通过80端口访问时，一般的浏览器会默认不安全，不让你访问，而vivo浏览器则全部放行，这一点我深有体会，收益颇多。

在服务器终端可以输入bt来查看宝塔的命令行,一般都是14，来看宝塔登录地址和你的账号密码。

进去后一般都要下nginx。我的理解是它就像一个管家，它会首先接收你的访问请求，如果访问的是静态数据，比如图片，文字等等那么就直接在服务器文件夹对应位置找出文件扔给用户。如果访问的是一个动态数据，比如留言编辑等等，他会把请求发给正在运行的后端代码处理，处理完之后再扔给你看。

如果你的项目有更厉害的架构就要下一些对应的东西，比如phpMyAdmin——数据库的图形化控制台，php——后端请求所需环境等等。但是这都是后话了。
## 实时git推送
对我来说，我的这个项目还在不断更新中，那每次更新是不是都要重新打包好然后传给我的服务器呢？按常理来说确实可以如此，但是借助Github的Actions特性和宝塔特有的git建站，就可以完成每次更新推送代码到Github实时更新我们服务器中的文件，网站呈现新的样貌这一整个自动化流程。

具体做法就是在宝塔的网站上点击Git部署，接着填写这个项目对应的Git地址和对应分支，域名(先写你的服务器ip地址)。接着在Github的Actions上文章，在你的项目根目录新建一个.github文件夹，在里面再新建一个workflows文件夹,接着再建一个deploy.yml文件，这个yml文件就是一整个工作流程序，在每次更新的时候会自动执行这个程序。
老实说我的yml的代码是从b站一个大佬那抄来的。

首先我要指出的是双括号里面的内容都是响应是数据，像一个字典，键和值都是要在GitHub中自己配置的。在最后一部分我会给出配置的步骤。
```yml
name: 自动化推送流程

on:
  push:
    branches:
      - main

jobs:
  deploy:
    runs-on: ubuntu-latest

    steps:
      - name: Checkout code
        uses: actions/checkout@v4

      - name: Setup Node.js
        uses: actions/setup-node@v4
        with:
          node-version: '20'

      - name: Install dependencies
        run: |
          cd blog
          npm install

      - name: Build project
        run: |
          cd blog
          npm run build

      - name: Deploy to server
        uses: easingthemes/ssh-deploy@main
        with:
          SSH_PRIVATE_KEY: ${{ secrets.SSH_PRIVATE_KEY }}
          REMOTE_HOST: ${{ secrets.SERVER_IP }}
          REMOTE_USER: ${{ secrets.SERVER_USER }}
          SOURCE: 'blog/dist/'
          TARGET: ${{ secrets.SERVER_PATH }}
          ARGS: '-avzr --delete'

      - name: Fix permissions
        uses: appleboy/ssh-action@v1
        with:
          host: ${{ secrets.SERVER_IP }}
          username: ${{ secrets.SERVER_USER }}
          key: ${{ secrets.SSH_PRIVATE_KEY }}
          script: |
            sudo chown -R www:www ${{ secrets.SERVER_PATH }}
            sudo find ${{ secrets.SERVER_PATH }} -type d -exec chmod 755 {} \;
            sudo find ${{ secrets.SERVER_PATH }} -type f -exec chmod 644 {} \;
```
这里的name可以随便改，on指得是每次有新的推送(push)到main分支时。而jobs就是一整个工作流： deploy是这个工作流的名称；runs-on是运行环境这里对应的是我服务器的ubuntu的linux环境，steps里面就是我具体的步骤。分为了五个具体的步骤，每一过程中uses指的是可以被GitHub识别的工具包，举这边的例子来说actions/checkout@v4指的是下载所有的源代码，actions/setup-node@v4指的是安装最新的node.js环境。

其中run里面的内容是运行在终端里面的，cd blog指到blog文件夹中，npm i(即npm install)指安装所有依赖(靠package.json文件)，npm run build指的是打包。

接着说说最后两步，这个Deploy to server步骤把打包的文件部署到服务器中去的，这里的easingthemes/ssh-deploy@main指的就是把文件从临时电脑里拿出来，通过网络塞进服务器这个工具包，with指用来传递要用的参数
```sh
SSH_PRIVATE_KEY: ${{ secrets.SSH_PRIVATE_KEY }}
```
这个指的是服务器的密钥，当临时电脑访问服务器时，通过密钥才获得实现更改服务器文件的能力
```sh
REMOTE_HOST: ${{ secrets.SERVER_IP }}
```
这个指的是服务器的ip地址，临时电脑就是通过这个地址联系起服务器
```sh
REMOTE_USER: ${{ secrets.SERVER_USER }}
```
这个指的是访问身份，如果你不确定可以在服务器中输入来查询
```sh
whoami
```
服务器会返回你的登录用户名，一般默认是root
```sh
SOURCE: 'blog/dist/'
```
这个指的是传送打包后的哪些文件，这里因为是vue框架，实际要的只是dist文件夹里面的。
```sh
TARGET: ${{ secrets.SERVER_PATH }}
```
这个指的放在服务器的哪里，如果你不清楚可以去查/www/server/panel/vhost/nginx下你域名的conf文件，和里面那个root要对应。
```sh
ARGS: '-avzr --delete'
```
这几个是干活的准则：a——保持所有文件属性不变，v——搬运的细节打印在日志里，z——把文件打包压缩后再传，r——dist里的子文件夹也搬，delete——对比服务器和搬运的文件夹，把服务器上的旧文件清除。

这个Fix permissions这一步存在的意义在于工作流中root用户上传的文件，一般通过443端口的访问者没有权限查看。所以这里换主人。
```sh
host: ${{ secrets.SERVER_IP }}
username: ${{ secrets.SERVER_USER }}
key: ${{ secrets.SSH_PRIVATE_KEY }}
```
这里指的是拿着这把密钥，去对应的IP地址，以这个用户名登录，然后在远程服务器上执行后面的指令
```sh
sudo chown -R www:www ${{ secrets.SERVER_PATH }}
```
这里的sudo指的是以管理员的身份运行，chown是Change Owner的缩写，-R指的是字文件夹也换，www:www指把所有者改成www用户，所属组改成www组,后面的那个是具体的目标地址
```sh
sudo find ${{ secrets.SERVER_PATH }} -type d -exec chmod 755 {} \;
```
find是一个查找提示符，type d指文件夹，找到后对其进行chmod 755操作，其中755指所有者即www可读、写、执行；Nginx即管家只能读和执行
```sh
sudo find ${{ secrets.SERVER_PATH }} -type f -exec chmod 644 {} \;
```
这里找的则是所有的文件，644指所有者可读和写；Nginx只能读。
## Github配置
在你的项目setings中的Secrets and variables子文件中设置中这些代码中被引用的数据，一共新建四个仓库秘密(Repository secrets),分别是SERVER_USER，不清楚的话可以在服务器中输下面的代码查询。
```sh
whoami
```
服务器会返回你的登录用户名，一般默认是root

接下来是SERVER_IP对应服务器的ip地址，如果忘了可以在服务器中输入
```sh
curl ifconfig.me
```

SERVER_PATH则是对应放到的位置：/www/wwwroot/你的域名

SSH_PRIVATE_KEY指的是密钥，非常重要，不能被别人随意拿到，因为这样别人就能随意支配你的服务器，就像把你的电脑密码泄露了一样危险，可以在服务器中输入
```sh
cat ~/.ssh/id_rsa
```
把服务器输出的所有内容全部复制粘贴，包括开头和结尾的-----BEGIN RSA PRIVATE KEY-----
